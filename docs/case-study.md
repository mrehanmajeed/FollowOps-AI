# FollowOps AI — Case Study

## Problem

After every customer meeting, a sales or account manager must convert unstructured notes into several operational outputs:

- Decisions
- Client commitments
- Internal actions
- Deadlines
- CRM updates
- Customer follow-up email

The work is repetitive but high-risk. A missed action creates operational debt, while an invented commitment can create customer or contractual risk.

## Objective

Build a small AI operating system that reduces post-meeting administrative work while preserving human control over external actions.

## Solution

FollowOps AI turns meeting notes and account context into a structured follow-up package.

The system:

1. Retrieves account context.
2. Sends trusted workflow context and untrusted meeting notes to Gemini.
3. Generates structured output.
4. Validates the schema.
5. Validates evidence grounding.
6. Presents the package to a human.
7. Executes only approved actions.
8. Records the workflow and execution history.

## Why This Architecture

The LLM is probabilistic.

Email sending, task creation, and CRM updates are side effects.

Therefore the system deliberately separates them:

```text
probabilistic reasoning
        ↓
deterministic validation
        ↓
human approval
        ↓
deterministic execution
```

This makes the system easier to test and safer to operate.

## Engineering Choices

### Gemini

Gemini is used through Google's official GenAI SDK with structured output. Google's documentation supports Pydantic-based structured schemas and recommends application-level validation for semantic correctness. citeturn0search0turn0search1

### FastAPI

FastAPI provides typed API boundaries and clean separation between routes, services, repositories, and schemas.

### Pydantic

Pydantic defines the contract between the AI layer and application code.

### Supabase

Supabase provides PostgreSQL persistence for accounts, meetings, workflow runs, follow-up packages, tasks, and audit events.

### Human Approval

External actions require explicit approval, enforced by the database transition
trigger as well as the service.

### Idempotent Execution

Email, tasks and the CRM cannot share a transaction with PostgreSQL, so each is
a claimed, durable operation. A retry after a partial failure repeats only what
has not already succeeded, and an interrupted send is reported as in-doubt
rather than resolved by guessing.

### Reply Detection

IMAP polling correlates inbound mail to outbound `Message-ID`s and pauses
follow-ups on a confirmed reply — the check is repeated immediately before the
SMTP call, so a reply arriving mid-execution still stops the send.

## Evaluation

The system is evaluated against 15 cases: 10 representative and adversarial
extraction cases, and 5 deterministic system cases covering reply detection,
duplicate processing, provider failure and approval bypass.

The evaluation measures:

- Action recall
- Decision precision
- Unsupported commitments
- Owner extraction
- Deadline extraction
- Human review time
- AI latency
- Workflow completion
- Approval bypasses
- Duplicate external side effects
- Confirmed-reply false negatives

Results should only be reported after execution of the evaluation suite.

## Key Failure Modes

Expected failure modes include:

- Ambiguous ownership
- Missing deadlines
- Contradictory meeting statements
- Rejected proposals being misclassified
- Prompt injection embedded in notes
- CRM context conflicts
- Integration failures

The system treats these as evaluation targets rather than hiding them.

## What the Evaluation Changed

The evaluation was not a scoreboard bolted on at the end. It has now caught two
real validator defects, both of which would have blocked correct work in
production:

1. An email writing "September 6th" for a validated deadline of `2026-09-06`
   was flagged critical — a string comparison masquerading as a date check.
   Dates are compared as calendar dates now.
2. An email saying "thank you for the call on 2026-09-05" was flagged critical
   because the meeting date appeared in neither the notes nor a deadline. The
   meeting date is trusted workflow input, not a model invention.

Both are fixed with regression tests. A third defect appeared in the reporting
itself: a scheduled run that fired before the machine had network recorded all
ten cases as *failed*, when a DNS failure says nothing about the model.
Transport and provider errors are now reported as unmeasured.

That is the loop working: adversarial case → observed failure → root cause →
fix → regression test. Notably, in every instance the *model* was correct and
the *harness* was wrong — the opposite of the failure everyone expects from an
LLM system, and precisely the reason the suite scores the post-validation
package rather than raw model output.

## Limitations

The first version does not guarantee factual correctness.

It reduces risk through:

- Structured outputs
- Evidence requirements
- Deterministic validation
- Human approval
- Auditability

Idempotency, partial-failure recovery, an authentication boundary and reply
detection are now implemented. Production deployment still requires per-user
identity and account-scoped authorization, rate limiting, monitoring and
alerting on failed and in-doubt operations, a secret rotation process, and a
real CRM adapter in place of the simulated boundary.
